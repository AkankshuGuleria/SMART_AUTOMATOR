## Problem 1 — Morning Brief shows "No brief available yet" 🔴

### Symptom
Clicking the **Brief** tab shows: `No brief available yet.`

### Root Cause
The backend's `GET /projects/{project_id}/brief` endpoint returns `{"brief": null}` because no brief
has ever been generated and persisted in the `daily_briefs` table in CockroachDB.

The brief is only generated by:
1. `POST /projects/{project_id}/restore` (restore workspace trigger), OR
2. The planner's `regenerate_daily_brief` action (only fires on `on_commit` or `on_session_end` triggers)

There is no UI button or chat command that triggers brief generation on demand for the first time.

### What needs to be added
In `server.py`, add a `POST /projects/{project_id}/brief/generate` endpoint that calls
`agent_actions.generate_project_summary()` and writes the result to `daily_briefs` via
`db.client.upsert_daily_brief()`. Then add a **"Generate Brief"** button to the Brief screen in
`MorningBriefWrapper.tsx`.

Alternatively, when the chat receives the "morning brief" intent, the `_execute_chat_morning_brief`
action in `planner.py` should upsert the result into the database — right now it only computes the
brief payload in memory but never persists it.

### Files involved
- `backend/api/server.py` — add `/projects/{project_id}/brief/generate` endpoint
- `backend/decision_engine/planner.py` — `_execute_chat_morning_brief` should call `upsert_daily_brief`
- `frontend/src/components/MorningBriefWrapper.tsx` — add "Generate" button + re-fetch after

## Problem 2 — Vite proxy shows EADDRINUSE errors in logs 🟡

### Symptom
The `npm run tauri dev` log shows repeated errors:
```
[vite] http proxy error: /health
Error: connect EADDRINUSE 127.0.0.1:8000
```

### Root Cause
This is **specific to the Tauri native window** — Tauri spawns its own web view that talks
**directly to localhost:8000**, but the **Vite dev server process** (on port 5173) is also
trying to proxy requests to the same backend. The two paths collide on certain health-check polling.

The Tauri webview uses the Vite server as its dev URL, which means health checks hit Vite's
proxy. When the backend is already bound to port 8000, the proxy connection attempt from Vite
itself (not from the webview) throws `EADDRINUSE` if any misconfiguration causes it to try
binding rather than connecting.

**The app still works despite this error** — the webview sees 200 OKs. It's a noisy log warning,
not a functional failure.

### What needs to be fixed
In `vite.config.ts`, verify that all proxy entries use `target: 'http://127.0.0.1:8000'` and
`changeOrigin: true` only (not `ws: true` on the HTTP routes, which can cause spurious
reconnection attempts).

Also see `src-tauri/tauri.conf.json` — if `devUrl` is set to `http://localhost:5173`, confirm
the tauri `beforeDevCommand` waits for the Vite server to be ready before launching.

## Problem 3 — Chat action card shows "open browser to open browser to chatgpt.com" 🟡

### Symptom
After sending "open browser to chatgpt.com", the action card provenance says:
> `Executed: open browser to open browser to chatgpt.com`

The phrase "open browser to" is duplicated in the provenance string.

### Root Cause
In `planner.py`, `_get_actions_for_trigger()` constructs the provenance using `target`, which is
set by the intent parser to the **full raw message** ("open browser to chatgpt.com"). The provenance
template then prepends "Executed: open browser to " — so the raw message gets double-prefixed.

### Fix
In `planner.py`, for the `chat:open_browser` trigger, use the resolved URL/app name from
`agent_actions._resolve_app_target()` in the provenance string — not the raw message.

Or strip the prefix in `_get_actions_for_trigger`:
```python
if trigger == "chat:open_browser":
    # target is the raw message; resolve it for clean provenance
    from agent_actions import _resolve_app_target
    _, resolved = _resolve_app_target(target)
    return [{"type": "chat_open_browser", "policy": ...,
             "provenance": f"Executed: opened {resolved}"}]
```

### Files involved
- `backend/decision_engine/planner.py` — `_get_actions_for_trigger()` around line ~430–440

## Problem 4 — Bedrock / Embedding show as "not_configured" 🟡

### Symptom
`/health` returns:
```json
{ "bedrock": "not_configured", "embedding": "not_configured" }
```
This means intents like "explain repo", "what was I working on yesterday?", "continue work" etc.
will return empty replies because `invoke_reasoning()` returns `None` and there are no embeddings
for vector search.

### Root Cause
The AWS Bedrock credentials or the embedding model endpoint are not set in the
`.env` file. These were marked as "deferred" in earlier phases.

Specifically, `backend/config.py` checks for `BEDROCK_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`
and `EMBEDDING_MODEL_ID`. If these are blank, `ai/bedrock_client.py`'s `invoke_reasoning()` returns `None`.

### What needs to be configured
In `backend/.env`, set:
```env
BEDROCK_REGION=us-east-1
AWS_ACCESS_KEY_ID=your_key
AWS_SECRET_ACCESS_KEY=your_secret
BEDROCK_MODEL_ID=anthropic.claude-3-haiku-20240307-v1:0
EMBEDDING_MODEL_ID=amazon.titan-embed-text-v2:0
```

Without Bedrock, these intents still show an empty result but won't crash:
- "explain repo" — returns architecture notes only, no AI synthesis
- "what was I working on?" — returns raw memory bullets, no AI summary
- "generate commit message" — returns a default fallback message

### Files involved
- `backend/.env` — set AWS credentials (DO NOT commit to git)
- `backend/.env.example` — already has the right variable names

## Problem 5 — React key prop warning in ChatPanel 🟡

### Symptom
Browser console shows:
```
Each child in a list should have a unique "key" prop.
Check the render method of `ChatPanel`.
```

### Root Cause
The `parseMarkdownLike()` function signature was updated to accept `msgId` for unique key
generation, and the call site was updated. However the compiled Vite bundle in the running
Tauri dev session hasn't hot-reloaded the new code (Tauri dev requires the Vite HMR to connect
through the same port that the proxy error occurs on).

### Fix
After the Vite proxy EADDRINUSE issue is resolved (Problem 2), HMR will work and the key fix
already committed to `ChatPanel.tsx` will take effect. Or simply restart `npm run tauri dev`.
